# RunPodFarm v2 («rpfarm») — дизайн

Дата: 2026-09-02. Статус: согласован с владельцем, ждёт план реализации.
Репо: MAY4VFX/houdini_runpod_scheduler. Роль: vfx.

## 1. Цель и UX

Артист в Houdini нажимает Cook. Дальше без его участия: зависимости хипа уезжают на
ферму, поднимаются GPU-поды RunPod, считают рендер или симуляцию, результаты
приходят обратно **ровно в те локальные пути, куда были нацелены ROP-ноды**, поды
гаснут. Прогресс всех стадий виден как work items в PDG, Houdini не блокируется.

Новый пользователь стартует за три команды: клонировать репо, `rpfarm setup`
(ключ RunPod, всё остальное автоматически), первый кук. Никаких своих серверов,
консолей и VPN. Единственные интерфейсы — TOP-ноды в Houdini и CLI `rpfarm`.

Модель использования: одна ферма на одном аккаунте RunPod, несколько доверенных
пользователей, каждый со своим API-ключом RunPod (ключи создаются и отзываются в
консоли RunPod). Тот же репо разворачивается и на чужом аккаунте той же командой
`setup` — отличается только введённый ключ.

## 2. Что было не так в v1 (факты по коду, 2026-09-02)

- Цепочка доставки файлов не замкнута: HDA заливал `$JOB` в B2, воркер клал файлы в
  `/workspace/tasks/<id>/input`, а команда PDG ждала их в `/project`. Ничего не
  писало в `/workspace/projects`.
- Результаты назад: воркер собирал `/workspace/tasks/<id>/output`, куда Houdini не
  пишет; HDA качал весь префикс `results/` после каждой задачи и не распаковывал `.zst`.
- Heartbeat парсился как ISO-дата, а был JSON: всегда исключение, поды никогда не
  считались мёртвыми; задачи упавших подов не перевыставлялись.
- Автоскейл-даун недостижим (ранний `return`), `rpfarm_idletimeout` нигде не читался.
- SHA-256 всех зависимостей пересчитывался на **каждый** work item.
- PDG MQ стартовал на машине артиста, поды должны были подключаться к ней входящим
  соединением — за NAT невозможно.
- Три хранилища (B2, Network Volume, JuiceFS) и домашний Redis через Oracle-socat как
  точка отказа. Сервер, дашборд, auth-api, desktop-app — вокруг JuiceFS, который на
  RunPod не работает (нет FUSE).
- Шаблон RunPod `4tee2rtpu4` хранит пароль Redis в env открытым текстом.

Единственная концептуальная ошибка v1 — JuiceFS и всё, что выросло вокруг него.
Сбор зависимостей, компрессия, cost tracker, идея cache manager — переиспользуются.

## 3. Архитектура

```
Houdini (артист)                              RunPod (EU-RO-1)
┌───────────────────────────────┐            ┌──────────────────────────────────┐
│ rpfarm_upload   (TOP)  ───────┼─ sftp ────►│ sync-под (CPU, ~$0.07/ч)         │
│ rpfarm_scheduler(TOP) ────────┼─ HTTPS ───►│  sshd · rclone · worker.py       │
│    │ PDG MQ client ◄──────────┼─ tcp ──────│  mqserver (PDG, hython с volume) │
│ rpfarm_download (TOP) ◄───────┼─ sftp ─────│  housekeeping (du/ls/rm/ledger)  │
│ rpfarm_stats    (TOP)         │            │           │ /workspace           │
│ CLI rpfarm                    │            │   Network Volume (один, зоны)    │
└───────────────────────────────┘            │           │ /workspace           │
                                             │ GPU-поды ×N (живут только пока   │
                                             │  есть задачи): worker.py, hython │
                                             │  hserver → lic.ai-vfx.com:1715   │
                                             └──────────────────────────────────┘
```

Домашняя инфраструктура участвует только лицензиями: `lic.ai-vfx.com:1715` →
Oracle socat (`lic-proxy.service`) → домашний sesinetd (адрес — в `departments/infra/map.md` штаба, в отслеживаемые файлы домашние IP не пишем). Tailscale не нужен: поды не могут поднять
TUN, а всё остальное идёт через публичный IP/прокси RunPod. Redis, B2, JuiceFS,
сервер на Dokploy — удаляются.

### 3.1 Компоненты

| Компонент | Где | Роль |
|---|---|---|
| `rpfarm/` (Python-пакет) | машина артиста, внутри Houdini Python 3.11 и как CLI | клиент RunPod REST, синк (rclone), сбор зависимостей, диспетчер, журнал |
| `rpfarm_upload` HDA (TOP processor) | Houdini | work items = пакеты файлов → sync-под |
| `rpfarm_scheduler` HDA (TOP scheduler, PyScheduler) | Houdini | поды, диспатч, MQ, автоскейл, бюджет, автоскачивание выходов, вкладка Farm |
| `rpfarm_download` HDA (TOP processor) | Houdini | work items = пакеты файлов ← sync-под |
| `rpfarm_stats` HDA (TOP processor) | Houdini | аналитика: журнал + биллинг RunPod как work items и итоги |
| `pod/` Dockerfile + `worker.py` + `entrypoint.sh` | образ `ghcr.io/may4vfx/rpfarm-pod` | один образ для sync- и GPU-подов; Houdini берётся с volume |
| CLI `rpfarm` | терминал | setup, doctor, storage, houdini, farm, costs, smoke |

Удаляется из репо: `server/`, `dashboard/`, `auth-api/`, `desktop-app/`, `AWSECS/`,
`infrastructure/provision.py`, `infrastructure/setup-juicefs.sh`, старый `docker/`,
старый `worker/` (executor и compression переезжают), `.worktrees/`.

### 3.2 Sync-под

CPU-под (флейвор `cpu3c`/`cpu5c`, 2–4 vCPU, EU-RO-1) с примонтированным volume,
публичным IP и портами `22/tcp` (sshd), `8000/http` (worker), два `tcp` для MQ.
Поднимает первая нода, которой он нужен; переиспользуется всеми; гаснет по
idle-таймауту (параметр, по умолчанию 15 мин без активных задач и синков) либо
`rpfarm farm kill`. Имя: `rpfarm-sync-<user>`. Одновременно один sync-под на
пользователя; GPU-поды его не заменяют (заливка идёт на дешёвый CPU).

Факты спайка (2026-09-02, EU-RO-1, флейвор `cpu3c`, 2 vCPU, `cloudType: SECURE`,
volume `2ze7qdwkt3`): `POST /v1/pods` с `computeType: "CPU"`, `cpuFlavorIds`,
`vcpuCount`, `dataCenterIds: ["EU-RO-1"]`, `networkVolumeId`, `volumeMountPath`,
`ports: ["22/tcp","4440/tcp","4442/tcp","8000/http"]`, `supportPublicIp: true`
создаёт под и подключает volume без ошибок — CPU-поды с volume в EU-RO-1
работают. Под стал `RUNNING` с присвоенным `publicIp` и заполненным
`portMappings` за **19 секунд**. Ответ `GET /v1/pods/{id}` отдаёт публичный IP
в поле `publicIp` (строка) и маппинг портов в `portMappings` — объекте вида
`{"<internal-port>": <external-port int>}`, например
`{"22": 21829, "4440": 21830, "4442": 21831}`; `8000/http` в `portMappings` не
попадает (http-порты не мапятся напрямую, доступ только через
`https://<podId>-8000.proxy.runpod.net/` — прокси подтверждён, `curl` вернул
200 за 0.48с). `nc -vz <ip> <external-port>` подтвердил, что внешние TCP-порты
4440/4442 открыты и достижимы с внешней машины. `costPerHr` для `cpu3c`/2vCPU —
**$0.06/ч**.

`mqserver` из `/workspace/houdini/bin/mqserver` (Houdini 20.5.684 с volume,
`source houdini_setup_bash` из `/workspace/houdini`) запускается и слушает без
GPU на CPU-поде; connection-файл (`-c /tmp/mq.txt`) содержит
`PDG_MQ <internal-ip> 4440 4440 4442`. Единственная граница, на которую стоит
обратить внимание в реализации: `source <file> | tail` (или любой пайп) в bash
исполняет `source` в сабшелле — переменные окружения (`PATH`, `HFS`) теряются
после пайпа; `rpfarm/pods.py` должен звать `source houdini_setup_bash` без
пайпа в той же команде, что и `mqserver`/`hython`.

Факты по загрузке пода (2026-09-02, Task 4, образ `ghcr.io/may4vfx/rpfarm-pod`):

- **`set -u` и `houdini_setup_bash` несовместимы.** Скрипт SideFX читает
  переменные, которых сам не задаёт (на 21.0.792 это `SHFS`, на других сборках
  `PYTHONPATH`/`LD_LIBRARY_PATH`), а так как его делают `source`, аборт по
  unbound variable убивает **саму оболочку entrypoint**, а не сабшелл. Именно это
  четыре раунда выглядело как «под не поднимается»: контейнер падал сразу после
  запуска sshd, RunPod перезапускал его каждые ~17 секунд, а снаружи это читалось
  как «`publicIp`/`portMappings` появились и исчезли, SSH refused, `/health` 404».
  Любой код, который делает `source houdini_setup_bash`, обязан снимать `set -u`
  на время вызова (`build_shell_command` в `worker.py` безопасен: он работает в
  `bash -c` без `set -u`).
- **Boot-лог живёт на volume.** Логи контейнера RunPod доступны только в его
  веб-интерфейсе, программно их не прочитать. Поэтому entrypoint дублирует весь
  свой stdout+stderr (включая вывод `worker.py` после `exec`) в
  `/workspace/ledger/logs/boot-<podId>-<epoch>.log`. Volume переживает под, так
  что следующий под или ssh-сессия читают, почему умер предыдущий — это
  единственный способ диагностики недоступного пода. Крашлупящийся под пишет по
  файлу на перезапуск, поэтому housekeeping (Task 12) должен чистить
  `boot-*.log` по возрасту/количеству.
- **Cloudflare перед `proxy.runpod.net` режет `Python-urllib/3.x`** — отдаёт
  `403` там, где `curl` получает настоящий ответ. Любой HTTP-клиент к прокси
  (в частности `WorkerClient`, Task 7) обязан слать браузерный `User-Agent`,
  иначе он неверно прочитает каждый ответ.
- **`lastStatusChange` не является признаком рестарта** — поле осталось на
  «Rented by User» через 52 перезапуска контейнера. Здоровье пода определяется
  только опросом `/health`, не полями пода в REST.
- **Образ не должен нести CUDA runtime.** База переведена с
  `nvidia/cuda:12.4.1-runtime-ubuntu22.04` на `ubuntu:22.04`: драйвер и `libcuda`
  на GPU-подах инжектит контейнерный рантайм RunPod, а тулкит в образе стоил
  1310 MiB, которые оплачивались при каждом холодном старте. Слои сжались с
  1505.8 MiB до 137.5 MiB (−90.9%).
- **Тайминги живого пода** (CPU, `HOUDINI_VERSION=.`, volume `2ze7qdwkt3`):
  `/health` 200 через **43.5 секунды** после `POST /pods`, ровно один boot-лог.
  `hserver -S lic.ai-vfx.com:1715` отработал (`Successfully changed server
  listing.`), `hserver -l` показал `Connected To: http://lic.ai-vfx.com:1715`
  (`sesinetd22.0.368`, Houdini 20.5.684), а `hou.licenseCategory()` вернул
  `licenseCategoryType.Commercial` — лицензия реально берётся с фермы. Первый
  запуск `hython` с volume занял **~104 секунды** (холодный кэш сетевого диска);
  таймауты в `WorkerClient` должны это учитывать. Безобидный шум в логах:
  `hserver` пишет `sh: 1: systemctl: not found` и всё равно работает.

### 3.3 GPU-поды

Создаются шедулером через `POST /pods`: шаблон `rpfarm-pod`, volume, `supportPublicIp`,
GPU из приоритетного списка ноды (первый доступный в стоке EU-RO-1 — для этого в теле
запроса `gpuTypePriority: "custom"`, а не дефолтный `"availability"`: по openapi
`"custom"` значит «всегда пытаться арендовать типы в порядке `gpuTypeIds`», тогда как
`"availability"` порядок игнорирует и берёт то, чего у RunPod больше. Разница в цене
трёхкратная: в живом smoke с `"availability"` вместо A4500 (~$0.25/ч) достался
RTX 4090 за $0.740/ч. То же для `cpuFlavorPriority` на sync-поде), env:
`RPFARM_TOKEN`, `RPFARM_ROLE=gpu`, `PDG_RESULT_SERVER=<sync-ip>:<mq-port>`,
`SESINETD_HOST/PORT`, `HFS=/workspace/houdini/<version>`. Имя:
`rpfarm-<user>-<project>-<cook8>-<n>`. Живут только пока шедулер держит для них
задачи; гаснут по idle-таймауту и в `onStopCook`.

### 3.4 worker.py (на каждом поде)

Stdlib-HTTP-демон, ~200 строк, токен в заголовке. Эндпоинты:
`GET /health` (роль, слоты, gpu, uptime, активные задачи), `POST /tasks` (cmd, env,
cwd → task_id), `GET /tasks/{id}` (state, exit_code, started/ended, tail лога),
`GET /tasks/{id}/log`, `DELETE /tasks/{id}` (kill), `POST /exec` (только sync-под:
короткие служебные команды — mqserver, du, ls, rm, tar), `GET /exec/{handle}`
(статус открепления). Доступ снаружи через `https://<podId>-8000.proxy.runpod.net`.

**`/exec` — только для коротких команд; долгие идут через `detach: true` (Ruling R31).**
Прокси RunPod стоит за Cloudflare и рвёт ответ примерно на 100-й секунде, поэтому
синхронный вызов длиннее этого физически недоставляем (`timeout_s` зажат до 90 с).
Цепочка отказа, стоившая Task 14 одной установки Houdini: прокси обрывает ответ на
~100 с → на своей отметке `subprocess.run(timeout=)` шлёт SIGKILL порождённому shell
и закрывает его stdout-pipe → но установщик SideFX — **внук**, он этот SIGKILL
переживает и продолжает распаковку → на следующей записи прогресса в закрытый pipe
получает SIGPIPE и умирает уже после главного tar, но до `install_python` → на диске
остаётся 11 ГБ, выглядящих как готовая установка, без каталога `python/`, и hython
падает на `libpython3.13.so.1.0`. Проверка «файл `bin/hython` на месте» такую
установку принимает. Поэтому: `detach: true` пишет команду в скрипт, запускает её в
отдельной сессии с выводом **в файл** (а не в HTTP-pipe), сразу отдаёт `202` с
`handle`/`log_path`/`rc_path`; код возврата пишется в `.rc` последним действием и
переживает рестарт воркера; вызывающий опрашивает `GET /exec/{handle}` и читает лог
через `GET /files`. Таймаут по размеру пакета остаётся, но как **дедлайн наблюдения**:
его достижение прекращает опрос и сообщает об этом, не трогая саму команду.
Синхронный путь при таймауте убивает всю группу процессов, а не только shell.

Задача = `bash -lc` с `source $HFS/houdini_setup_bash` и переданным окружением PDG;
stdout/stderr стримятся в файл лога на volume (`/workspace/ledger/logs/<cook>/<task>.log`),
чтобы лог переживал под.

### 3.5 Синк: rclone по sftp

Артист-сторона. `rpfarm setup` скачивает статический бинарь rclone под ОС (macOS,
Linux, Windows) в `~/.rpfarm/bin`, генерирует ключ SSH `~/.rpfarm/id_ed25519`;
публичный ключ передаётся подам в env `PUBLIC_KEY` при создании (entrypoint кладёт его
в `authorized_keys`). Передача: `rclone copy --files-from <пакет> --transfers 4
--checkers 8 --sftp-*`, инкрементально по размеру+mtime. Компрессия: опциональная
стадия (см. 4.3).

Абстракция `SyncBackend` с одной реализацией `SftpBackend`; интерфейс оставлен, чтобы
позже добавить `S3Backend` (RunPod S3-API волюма, endpoint `s3api-eu-ro-1.runpod.io`),
если понадобится заливка без пода. Сейчас не реализуется.

### 3.6 PDG-результаты: MQ на ферме

Шедулер использует штатный механизм PDG «MQ на ферме» (как HQueue/Tractor в режиме
Farm): `mqserver` запускается на sync-поде через `/exec`, слушает два tcp-порта,
шедулер подключается по публичному IP sync-пода и его внешним портам, GPU-поды
получают тот же адрес в `PDG_RESULT_SERVER`. `pdgcmd.addOutputFile` и статусы работают
штатно. Параллельно шедулер опрашивает `/tasks/{id}` — источник истины по
завершению и exit code; MQ — источник выходных файлов и атрибутов. Ignore RPC
errors = «When cooking batches» (как у HQueue).

### 3.7 TLS изнутри Houdini

Houdini поставляется со своим OpenSSL, у которого вкомпилированные пути к CA указывают
на сборочную машину SideFX (`/Users/prisms/builder-new/.../ssl/cert.pem`). На машине
любого пользователя этого пути нет, поэтому под `hython` `ssl.create_default_context()`
возвращает контекст с **нулём** сертификатов, и любой https-запрос падает с
`CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`. Это ломает весь
транспорт v2 разом: REST RunPod, GraphQL-запрос баланса и каждый вызов `WorkerClient`
через `*.proxy.runpod.net` — первый живой smoke умер на этом в `onStartCook`, не создав
ни одного пода. Поэтому **любой https-вызов, который делается изнутри Houdini, обязан
идти через `rpfarm.tls.ssl_context()`** (`urlopen(..., context=rpfarm.tls.ssl_context())`):
модуль ищет настоящий CA-бандл в `RPFARM_CA_BUNDLE`, `SSL_CERT_FILE`, `certifi` (если
импортируется) и в системных путях платформы, и строит из него проверяющий контекст.
Проверка сертификата никогда не отключается: по этим соединениям идут API-ключ аккаунта
и токен воркеров. Касается Task 9 (upload-нода), Task 10 (download-нода) и Task 13 (CLI,
когда его запускают под `hython`).

## 4. Данные

### 4.1 Volume: одна сущность, зоны

Один Network Volume `rpfarm-<owner>` в EU-RO-1 (пользователь решил: один volume,
директории под сущности; растить через `PATCH /networkvolumes/{id}`).

| Зона | Содержимое | Кто пишет | Чистка |
|---|---|---|---|
| `/workspace/houdini/<ver>/` | установленные Houdini (22.0.393 сейчас) | upload-пресет / CLI | `rpfarm houdini rm <ver>` |
| `/workspace/apps/` | плагины, Python-окружения, дистрибутивы | upload custom | вручную |
| `/workspace/projects/<user>/<project>/` | зависимости хипа, выходы | upload, задачи | `storage rm`, `storage prune` |
| `/workspace/ledger/` | журнал задач, логи | шедулер, worker | никогда (ротация логов > 90 дней) |
| `/workspace/.rpfarm/` | индекс использования (размеры, mtime, владелец) | housekeeping | служебное |

Ограничение RunPod, зафиксированное осознанно: **ресайз только вверх**, удаление файлов
не уменьшает счёт. Для этого есть `rpfarm storage recreate --size N`: создать новый
volume, поставить туда Houdini (пресет), переключить конфиг, старый удалить; проекты
пересинхронизируются при следующем куке (локальная копия — источник правды).
Ресайз вверх автоматический: при заполнении > 85% перед заливкой шедулер/upload
увеличивает volume на нужный объём (с округлением до 10 ГБ) и пишет об этом в лог ноды.

Текущий volume `2ze7qdwkt3` (50 ГБ, Houdini 20.5.684) переиспользуется: 20.5 удаляется,
22.0.393 ставится, размер растёт по потребности.

**Ловушка, проверенная вживую (Task 12, Ruling R27):** изнутри пода `shutil.disk_usage`
(и любой `statvfs` на `/workspace`) показывает ёмкость backing storage pool хостовой
машины, а не реальный/оплаченный размер network volume — на настоящем 50 ГБ volume это
дало ~2.14 PiB. У пода нет ключа RunPod API, чтобы узнать реальный размер самому; его
обязан передавать вызывающий (`RunPodAPI.get_volume(volume_id)["size"]`, кешируется —
`rpfarm.packages.get_volume_size_gb`). `pod/housekeeping.py`'s `ls`/`disk-usage` берут
размер только через `--volume-size-gb`; без него `total`/`used_pct` — `null`, а не
подставленное число из `shutil.disk_usage`.

### 4.2 Зависимости и маппинг путей

`rpfarm/deps.py`: `hou.fileReferences()` (раскрытые `$HIP/$JOB`, `$F`, UDIM, папки
секвенций целиком) + сам `.hip` + входные файлы work items апстрима. Никакого ручного
выявления. Хеширования нет; сравнение делает rclone.

PDG Path Map: `$JOB` ↔ `/workspace/projects/<user>/<project>`. Файлы вне `$JOB`
уезжают в `…/<project>/_ext/<абсолютный путь без корня>` и получают отдельные записи
в path map, так что хип на поде находит их без правок. `$HIP` вне `$JOB` — та же
логика.

Выходы: work item сообщает выходной файл (удалённый путь) через MQ; шедулер
делокализует его и ставит в очередь скачивания **сразу**, не в конце кука. Файл
ложится ровно туда, куда был нацелен ROP. `rpfarm_download` в режиме «Upstream
outputs» делает то же для всего апстрима (для повторного забора), в режиме «Custom
paths» — любые пути volume → локально.

### 4.3 Компрессия (переиспользуется из v1)

Опциональная стадия заливки в `rpfarm_upload`: `classify_file` из v1 решает по типу
и пробе сжимаемости; `.hip`, `.abc`, `.usd*`, несжатые VDB/bgeo → zstd на лету в
staging, на sync-поде post-шаг распаковывает. Уже сжатые (`.bgeo.sc`, `.exr` с
компрессией, `.rat`, `.tex`) пропускаются. Включается параметром ноды, по умолчанию
включена для uplink < 200 Мбит/с (измеряется в `doctor`).

### 4.4 Журнал и стоимость

- **Детали задач**: шедулер пишет `/workspace/ledger/<user>/<cook_id>.jsonl`, запись на
  work item: `cook_id, user, project, node, item, frame, pod, gpu, started, ended,
  duration_s, exit_code, cost_est`. `cost_est` = тариф пода × длительность + доля
  простоя пода в этом куке.
- **Локальная копия**: в конце кука и по кнопке «Sync ledger» новые записи (свои и
  чужие, что есть на volume) тянутся в `~/.rpfarm/ledger/`.
- **Деньги (истина)**: `GET /billing/pods` и `GET /billing/networkvolumes` RunPod по
  именам подов `rpfarm-<user>-<project>-<cook8>-*`. Видит всех пользователей аккаунта.
- **`rpfarm_stats`**: сшивает журнал и биллинг, work item = задача, поля = атрибуты;
  параметры-фильтры (период, проект, пользователь); итоги в UI ноды: $ всего, GPU-часы,
  $/кадр, разбивка по проектам и людям, стоимость volume, кандидаты на чистку
  (проекты без куков > N дней, с $/мес). Кнопка CSV. CLI-эквивалент `rpfarm costs`.

**rpfarm_stats** — Source: local ledger + RunPod billing; фильтры; итоги; CSV.

## 7. Ошибки и границы

- Под умер (нет `/health` 60 с): его задачи → ретрай на другом поде (до 2), потом fail
  work item. Логи на volume сохраняются.
- Houdini закрылся/кук отменён: `onStopCook` гасит поды кука; сироты (по префиксу
  имени и cook_id без живого шедулера) показываются в Status и убираются `farm kill`.
  При старте любого кука шедулер сначала ищет сирот своего пользователя и предлагает
  их убить.
- **Нет свободных машин — это ожидание, а не отказ кука (Ruling R32).** Наши поды не
  спотовые: `cloudType` `SECURE`/`COMMUNITY`, `interruptible` не задаётся никогда —
  значит занятый под у нас не отбирают, и единственный вопрос это наличие свободного
  на данную минуту. Поэтому кук, которому на старте не дали ни одного пода, **не
  падает**: айтемы копятся в очереди (`should_defer` считает пустой пул за один под,
  так что первый айтем всё равно принимается), тик продолжает поднимать поды со своим
  бэкоффом, а у каждого айтема свой дедлайн ожидания («Wait For Capacity», по
  умолчанию 15 минут). Истёк — проваливается **ровно этот айтем** через
  `fail_pending` → `workItemFailed`, и повторный кук перезапустит только его, а не
  весь граф. Фатально (`CookError`) остаётся то, чего ожидание не лечит: 4xx —
  неверный ключ, отсутствующий шаблон, кривой запрос; `is_capacity_error` разделяет
  4xx и 5xx/«нет ёмкости». Перебор списка GPU-приоритетов работает как раньше;
  `COMMUNITY` дешевле и часто имеет машины, когда `SECURE` пуст, — это практический
  выход из нехватки, и он вынесен параметром Cloud Type. Volume привязан к своему
  датацентру; смена DC = `storage recreate` в другом DC (тот же механизм).
- **То же правило — для sync-пода.** Нехватка бьёт в двух местах, и второе опаснее:
  sync-под поднимается первым, и без него кук не начинается вообще
  (`ensure_sync_pod` ронял кук сырым 500 — вживую RunPod не имел CPU-машин в
  EU-RO-1 ~2.5 минуты). Тот же дедлайн (тот же параметр Advanced, не второй), тот
  же Cloud Type, тот же разбор 4xx/5xx; бэкофф с джиттером, и лок берётся на каждую
  попытку отдельно, а не удерживается на всё ожидание, — иначе соседний waiter не
  сможет подхватить под, появившийся тем временем. Если по истечении лимита машины
  так и нет — здесь `CookError` уместен: проваливать поштучно нечего, не запустилось
  ничего. Текст называет, сколько ждали, где, и что делать дальше.
- **Наблюдение (механизм НЕ установлен): промежуточные файлы рендера на общем
  томе теряют кадры.** Форма отказа, воспроизведённая вживую: Karma ROP с
  `savetodirectory` = `$HIP/usd/$RENDERID` (то есть каталог на сетевом волюме,
  общий для всех подов кука), `Min Pods 2 / Max Pods 2 / Tasks Per Pod 1`,
  8 кадров — пришло 6. Все восемь задач: `exit_code 0`, work item'ы
  `CookedSuccess`, `items_failed: 0`, каждая сообщила путь своего выхода;
  файлов по двум из этих путей на волюме не появилось. Оба пропавших кадра —
  с одного пода, это его 2-я и 4-я задачи; второй под отдал все четыре.
  С одним подом (smoke, `minpods 1`) не воспроизводилось ни разу. После
  перевода пути на пер-подовый (`$HOUDINI_TEMP_DIR/rpfarm_usd/$RENDERID`) —
  три прогона подряд 8/8 (`28e76257`, `2b706124`, `8731a637`, `2213200a`).

  **Что именно ломается — неизвестно.** Правдоподобно, что `$RENDERID`
  (содержит pid) совпадает у одинаковых по счёту задач на двух свежих
  контейнерах, и они затирают друг другу промежуточный USD; но `$RENDERID` в
  тот прогон не логировался, каталог проекта стёрт, и гипотеза не проверена.
  Версия «параллель внутри одного пода» отпадает: `Tasks Per Pod = 1`, а слоты
  и есть предел одновременных задач на поде (`PodState.free_slots()`,
  `pick_pod()`), то есть задачи шли последовательно.

  **Правило, которое из этого следует и от механизма не зависит:** вывод
  рендера, кроме собственно кадров, пишется в скретч **пода**. Дефолт Houdini
  (`$HOUDINI_TEMP_DIR/usd_renders/$RENDERID`) уже такой и переопределять его на
  `$HIP`/`$JOB`/волюм нельзя. В README это записано как правило подготовки
  сцены; `scripts/build_demo_scene.py` его проверяет в `_verify()`.

- **Два разных path map, и ни один не дотягивается до USD (Ruling R44).**
  Кук 41f78681, задача `fetch_shot0012_4`, exit 1 за 42 с: сцена открылась,
  файл на поде был, а нода искала `/Users/may/BS/…` —
  «Unable to find layer file».

  **`PDG_PATHMAP` применяет не Houdini, а сам PDG** (`pdgcmd.localizePath`),
  то есть он накрывает только пути, которые резолвит PDG: hip, выходы,
  результаты айтемов. Путь USD-слоя внутри сцены через него не проходит вовсе.

  **`HOUDINI_PATHMAP` — переменная ядра Houdini.** Замерено на поде, с картой
  и БЕЗ каких-либо симлинков:

  | вызов | результат |
  |---|---|
  | `pathmap -t <локальный путь>` | смаплен |
  | `hou.findFile(<локальный путь>)` | путь на ферме |
  | `hou.hda.installFile(<локальный .hda>)` | **ok** |
  | `Ar.Resolve(<локальный путь>)` | `''` |
  | `Sdf.Layer.FindOrOpen(...)` | `None` |
  | кук стейджа | та же ошибка, что и без карты |

  Вывод фактом: **HOUDINI_PATHMAP не решает USD** — у USD свой резолвер, он про
  карту Houdini не знает. Зато он **решает задачу с приехавшими HDA**, которая
  стояла следующей: `hou.hda.installFile` по маковскому пути отработал. Поэтому
  переменная ставится в окружении задачи из той же карты, что и `PDG_PATHMAP`;
  оба механизма сосуществуют, PDG-карту не трогаем.

  **Недостающую половину поставляет сам SideFX.**
  `$HFS/toolkit/samples/USD/USD_HoudiniPathMapArResolver` (Apache 2.0) — резолвер
  ровно для этой задачи: его `_Resolve` прогоняет путь через
  `FS_Info::getPathOnDisk` (файловый слой Houdini, где и применяется
  `HOUDINI_PATHMAP`) и отдаёт результат `ArDefaultResolver`. То есть это мост
  между картой путей Houdini и резолвером USD — та самая половина, отсутствие
  которой было замерено выше.

  **Собран и проверен на поде (2026-09-05), БЕЗ симлинка и БЕЗ правки сцены:**

  | | до | после |
  |---|---|---|
  | `Ar.Resolve(<локальный путь>)` | `''` | `/workspace/projects/may/airship/BS/…usdc` |
  | `Sdf.Layer.FindOrOpen` | `None` | ok |
  | кук стейджа | «Unable to find layer file» | ok, 2 слоя |
  | кадр | нет | `final.exr`, 210 КБ |

  Парм в сцене при этом остался прежним — `/Users/may/BS/…` — и каталога
  `/Users` на поде нет.

  **Три факта сборки, каждый — реальный отказ, а не предосторожность:**
  компилятора в образе нет вообще; `hcustom` — это csh-скрипт («bad
  interpreter» без `csh`); и он безусловно линкует `-lGL -lX11 -lXext -lXi`
  даже для резолвера, который ничего не рисует, — компиляция проходит, падает
  ЛИНКОВКА. Плюс: в `usd_plugins/plugInfo.json` образца из macOS-установки
  стоит `.dylib`, в линуксовой — `.so`; берём образец из той Houdini, для
  которой собираем, и вопрос не возникает.

  **Где живёт:** в самой Houdini на томе (`$HFS/houdini/dso/usd/`), а не в
  образе. Он скомпилирован против USD-ABI этой версии Houdini, значит принадлежит
  ей: новая версия — новая сборка, пересборка образа его не теряет. Каталог
  `$HFS/houdini/dso/usd` уже на DSO-пути Houdini, поэтому куку не нужно никаких
  переменных. А компилятор и X/GL-заголовки не попадают в образ, который
  намеренно тонкий (жирный образ оплачивается на каждом холодном старте).
  Верхний `usd_plugins/plugInfo.json` образца — `{"Includes": ["*/resources/"]}`,
  побайтово то же, что у Houdini, так что копирование каталога ничего не затирает.

  **Устанавливается развёртыванием, а не руками:** шаг добавлен в
  post-команду пресета «Install Houdini from tarball»
  (`packages.usd_resolver_command`), то есть друг владельца, разворачивающий
  репозиторий с нуля, получает резолвер вместе с Houdini. Шаг не фатальный:
  рабочая установка Houdini ценнее, а провал сборки виден предупреждением.

  **Перекрывающиеся префиксы — замерено, а не предположено.** В нашей карте
  бывает корень, вложенный в другой (внешний каталог уехал в `_ext`, а его
  родитель — в зеркало проекта). На поде:

  * оба target'а существуют → Houdini берёт САМЫЙ ДЛИННЫЙ совпадающий префикс,
    вложенная запись выигрывает, файлы резолвятся правильно. Поэтому карта
    уходит целиком: выкинуть вложенную запись — значит отдать путь короткому
    корню и молча получить путь в зеркале проекта, где ничего нет;
  * **target не существует → запись молча деактивируется** (`pathmap` пишет
    «Not active. Target path not found.»), и путь забирает короткий корень —
    то есть НЕВЕРНЫЙ путь вместо отсутствующего. В куке это безопасно: каждая
    задача — новый процесс, а заливка к тому моменту закончена. Опасно только
    для файла, который не уехал вовсе (сняли галочку в окне).

  **`PXR_AR_DEFAULT_SEARCH_PATH` работает только для ОТНОСИТЕЛЬНЫХ путей** —
  проверено: относительный резолвится в файл на ферме, абсолютный игнорируется.
  Для абсолютной ссылки в сцене он бесполезен.

  **Симлинк локального корня отвергнут владельцем** («путь на ноде должен быть
  другой, мы не должны копировать мои пути») и откачен. Рабочая реализация была
  и доказана кадром, но воспроизводить локальные пути артиста на ферме — не наш
  подход, и это решение владельца, а не техническое ограничение.

  **Что РЕШАЕТ задачу нативно — правка сцены, и это рекомендация артисту, а не
  наша реализация.** Ссылка `$HIP/…` вместо абсолютной: Houdini разворачивает
  `$HIP` на обеих сторонах, а раскладка на ферме зеркалит локальную. Проверено
  на КОПИИ его сцены на поде (его файл не трогался):

      было:  /Users/may/BS/airship/Zeppelin_Balon_Test_Usd/Zeppelin_Balon_Test.usdc
      стало: $HIP/Zeppelin_Balon_Test_Usd/Zeppelin_Balon_Test.usdc
             -> /workspace/projects/may/airship/BS/airship/Zeppelin_Balon_Test_Usd/…
      стейдж: ok, 2 слоя, ошибок нет
      кадр:   rel.exr, 199 КБ

  То есть одна правка одного парма в его сцене чинит это без единой строки
  инфраструктуры — и то же самое сделает любую его сцену переносимой на любую
  ферму, включая чужую.

- **Зависимости, заданные ОКРУЖЕНИЕМ, приходится спрашивать по имени
  (Ruling R43).** `hou.fileReferences()` отдаёт пары `(Parm, path)`. У
  переменной окружения парма нет, значит её не найдёт ни наш сборщик, ни
  conductorовский, ни штатный Pre-Flight — никогда, ни при каком улучшении
  обхода. Это отдельный класс, и его надо перечислять руками.

  **$OCIO — тот случай, который бьёт молча.** У владельца
  `/Users/may/color/ocio/aces_2.0/config.ocio` (`may_aces-v2.0-baked_ocio-v2.1`,
  10 пространств). В контейнере пода OCIO не выставлен, и Houdini сам ставит
  его на свой конфиг с тома. Проверено на живом sync-поде:

      без OCIO:  name = cg-config-v3.0.0_aces-v2.0_ocio-v2.5
      с нашим:   name = may_aces-v2.0-baked_ocio-v2.1   (10 пространств)

  Рендер при этом НЕ падает: в сцене владельца почти нет явных имён
  пространств, там `auto`/`Automatic`/`linear`. Но что считать sRGB, а что
  линейным, решают правила ЗАГРУЖЕННОГО конфига — то есть кадры приезжают
  готовые и неправильные по цвету. Это худший вид дефекта из возможных.

  * **Едет каталог целиком, а не файл:** конфиг тянет LUT-ы рядом (у него
    `luts/`, 7 файлов, 23.3 МБ). В окне подтверждения это одна строка-папка с
    полным весом и источником `environment ($OCIO)`.
  * **На ферме переменная ставится в окружении ЗАДАЧИ** (`_ensureOcioEnv`,
    рядом с `PDG_PATHMAP`), а не в entrypoint: путь на ферме другой, и
    перевести его может только pathmap этого кука
    (`delocalize_via_pathmap`). Проверено: `/Users/may/color/ocio/aces_2.0/config.ocio`

    - **`hou.qt.styleSheet()` в живой сессии вернул 0 символов** — как и у
      тим-лида. Стиль живёт не в таблице стилей, а в Qt-стиле приложения;
      значит навесить его руками было бы тупиком, а брать готовые классы —
      единственный рабочий путь.
    - **`QStandardItem.setAutoTristate` — не `ItemIsAutoTristate`.** Проверено
      headless: с одним флагом снятая галочка ребёнка оставляла папку
      «отмеченной», то есть свёрнутая строка врала. Обе стороны (папка→дети,
      дети→папка) сделаны руками в обработчике `itemChanged`, массовые правки
      идут с заблокированными сигналами и одним пересчётом в конце.
    - `alternatingRowColors` выключен: под стилем Houdini полосы продолжаются
      ниже последней строки и заливают пустой вьюпорт — это ровно тот вид
      «отдельной программы», на который жаловался владелец.
    - **Правило про снимки:** offscreen-снимок из hython больше не считается
      доказательством внешнего вида. Снимок делается из живой сессии или не
      прикладывается вовсе.

  * **Окно — ДЕРЕВО, а не плоский список.** Решение владельца, дословно:
    «должно быть дерево с возможностью раскрыть до самого низа, но по дефолту
    только верхний открыт и галки можно снять на всех уровнях или поставить».
    Поводом был подсчёт: после глоббинга `outputimage` разворачивается во все
    уже отрендеренные кадры, и плоский список на сцене с 500 готовыми кадрами
    стал бы простынёй из 500 снятых строк. В дереве это одна свёрнутая строка
    с агрегатом.

    - Иерархия по каталогам до отдельного файла; цепочки папок с одним ребёнком
      схлопываются, иначе верхний уровень — это бесполезный `/`.
    - Раскрыт только верхний уровень.
    - Галочка на каждом узле, `Qt.ItemIsAutoTristate`: переключение папки несёт
      всё под ней, смешанное состояние показывается третьим состоянием — иначе
      свёрнутая строка врёт о том, что внутри что-то снято.
    - Вес и число файлов агрегируются на папке. Колонка «чем найдено» на папке
      показывает источник, только если он один на всё поддерево; смешанный —
      пусто, догадка там была бы враньём.
    - **Ответ пишется на том уровне, на котором принят**: снятая папка из 500
      кадров — одна запись в парме, а не 500 путей. Ближайший ответ побеждает,
      поэтому один файл, возвращённый галочкой внутри снятой папки, остаётся
      отмеченным. Обратная совместимость со старым голым списком сохранена.
    - **Обратно в набор для заливки**: папка, в которой ничего не сняли, уезжает
      ОДНОЙ ссылкой (её всё равно обойдёт `resolve_entries`), а папка со снятым
      файлом внутри заменяется списком оставшихся — ссылка не умеет выразить
      «всё, кроме вот этого».
    - Ненайденных файлов в дереве нет вообще: они идут строкой «нет на диске»
      внизу. У штатного Pre-Flight такие строки висят в дереве с прочерком
      вместо размера и снятой галочкой, и владелец справедливо читает это как
      ошибку.

  * **Пармы вывода теперь не выбрасываются, а показываются снятыми.** Это то,
    ради чего в штатном окне есть `forced_unselected_patterns`; раз окно наше,
    делаем то же самое своими силами. `pdg_workingdir` виден одной строкой с
    настоящим весом (11.5 ГБ), галочки на нём нет, и артист может её поставить —
    тогда грузится. Решение видно, а не спрятано.
  * **Ответ окна хранится в одном парме** `rpfarm_exclude`:
    `{"off": [...], "on": [...]}` — что сняли и какие пармы вывода вернули.
    Два умолчания (обычная ссылка отмечена, вывод снят) — но один ответ, один
    парм, одна запись в один момент; старый формат (голый список) читается как
    `off`, так что уже сохранённые сцены не теряют выбор.
    Штатное состояние Houdini (`include_all_refs=False`) не используем. Заодно
    проверено, что записать его из HOM нечем: `hou.Parm.setSelect`/`setAutoSelect` —
    это выделение канала в анимационном редакторе, к `include_all_refs`
    отношения не имеет; пишет его только само штатное окно.
  * **USD собирается объединением двух источников.** Композированный стейдж
    (что кук реально прочитает; на этой сцене материалы указывают на
    `tex_mip/*.exr`) ∪ `UsdUtils.ComputeAllDependencies` по каждому слою на
    диске (что нужно самому ФАЙЛУ слоя: незагруженный payload, невыбранный
    вариант; UDIM он раскрывает сам; на этой сцене — 71 исходный `textures/*.png`
    на 1.6 ГБ, которых рендер не читает). Объединение — потому что лишний файл
    стоит трафика, а недостающий — оплаченного часа GPU впустую. Второй источник
    выключается пармом `Scan USD Layer Files Too`. Скорость: стейдж 0.04 с,
    `ComputeAllDependencies` 0.02 с на слой, весь USD-обход 2.3 с на 5 ROP
    (включая кук стейджей) — жалобы сообщества на медленность подтвердить не
    удалось, но время логируется.
  * **`LopNode.stage()` на некукнутой ноде возвращает None — без ошибки.** В
    батче и в свежеоткрытой сцене это выглядит ровно как «в ветви нет USD», то
    есть целый стейдж текстур пропал бы молча. Ловится: кукаем один раз и
    спрашиваем снова, а если стейджа так и нет — говорим об этом в лог.
  * **Сверено с продакшн-сабмиттером Conductor** (`ciohoudini/assets.py`, открытый
    код). Три их решения взяты как есть, потому что они закрывают наши вопросы
    лучше придуманного нами, и одно из них независимо подтверждает нашу находку.

    - **Ручной список «тип ноды → пармы, которых нет в `fileReferences()`»**
      (`ADDITIONAL_PATH_PARMS`). У них первым и единственным пунктом стоит
      `Lop/reference::2.0: filepath1` — ровно тот случай, что нашёлся у
      владельца. Обход через `hou.nodeType(name).instances()`. Мы добавили
      только одно: имя, кончающееся цифрой, считается первым инстансом
      мультипарма, и соседи (`filepath2`, `filepath3`…) тоже читаются.
    - **Меняющиеся части пути — одним регекспом, а не набором частных случаев.**
      Дефолт их: `(_|\.)\d+(_|\.)|<udim>|<u>|<v>|<u2>|<v2>|<obj_name>`,
      совпадение заменяется на `*`, дальше glob по диску. Вынесен в парм
      `Varying Path Pattern`. Плата за общность: `<UDIM>` становится `*`, а не
      `[0-9][0-9][0-9][0-9]`, то есть сосед с тем же префиксом может приехать
      вместе с тайлами. Принято сознательно — лишний файл виден в окне отдельной
      строкой и снимается галочкой, а студия со своим соглашением об именах
      правит парм сама, не дожидаясь нас.
    - **`op:`/`temp:` пропускаем как внутренние, относительный путь пробуем от
      `$HIP` и от `$JOB`** и оставляем существующее (у них — то же самое, с
      честным комментарием «it's the best we can do for now»). Плюс их
      `asset_excludes` — у нас парм `Exclude Paths Matching`, glob-шаблоны через
      запятую, применяется к обеим половинам до открытия окна.
    - **Свои ноды не сканируем.** Они фильтруют `conductor::job`, мы —
      `runpodfarm*`: внутри нашего upload-ассета живёт свой `localscheduler`, чей
      `pdg_workingdir` равен `$HIP`, и без фильтра каталог всего проекта попадал
      в план строкой, которой артист туда не клал.

    Чего у них нет и что мы не копируем: обхода USD-стейджа. Они держатся на
    пармах Houdini плюс ручной список, и текстуру, прописанную внутри слоя, теряют.
    Наш `usddeps` строго полнее; объединение остаётся.

  * **`$F4` разворачивается в ТЕКУЩИЙ КАДР до того, как его кто-либо увидит.**
    Проверено: `hou.text.expandString("/x/sim.$F4.bgeo")` → `/x/sim.0001.bgeo`.
    Значит секвенция приезжала в сборщик как один конкретный файл, ветка
    «свести к каталогу» для неё не срабатывала НИКОГДА, и на ферму уезжал ОДИН
    кадр кэша. Дыра закрыта тем же регекспом: `.0001.` под него попадает.
    Это, а не UDIM, было самой дорогой из находок этого раунда — рендер по
    неполному кэшу не падает, он просто рендерит не то.

  * **UDIM раскрывается ДО проверки существования — и в парм-ветке тоже.**
    Литерального `Balon_Base_color_<UDIM>.exr` на диске нет. Что делал прежний
    код (уточнение к диагнозу «молча отбрасывал»): `<UDIM>` входил в регулярку
    последовательностей наравне с `$F`, поэтому ссылка сводилась к КАТАЛОГУ —
    файл не терялся, но ради шести плиток одного материала уезжала вся папка
    `tex_mip` (72 файла, 995 МБ). Теперь тайловый шаблон глоббится в реальные
    файлы (`<UDIM>` → `[0-9][0-9][0-9][0-9]`, прочие `<...>` → `*`), а покадровые
    `$F`/`%04d`/`####` по-прежнему сводятся к каталогу — там существующие на
    диске кадры не равны кадрам, которые прочитает ферма. Парм-половина сцены
    владельца: было 78 файлов / 1.2 ГБ, стало 65 файлов / 1.1 ГБ при том же
    наборе того, что рендер реально читает.
  * **UDIM и относительные пути в USD.** У шаблона `<UDIM>` `resolvedPath` ПУСТОЙ
    (11 из 16 asset-путей этой сцены — такие), раскрывается глоббингом по
    `[0-9][0-9][0-9][0-9]`. Относительный `./textures/...` тоже приходит с пустым
    `resolvedPath` и разрешается относительно СЛОЯ, который его написал, а не
    относительно cwd. Заодно нашлась настоящая поломка в сцене владельца:
    `0012box_and_camera.usdc` ссылается на `./textures/overcast_soil_puresky_7k_hdr.hdr`,
    которого в `shots/textures/` нет (файл лежит в `Zeppelin_Balon_Test_Usd/textures/`);
    `ComputeAllDependencies` показывает его как unresolved, и это теперь видно в логе.
  * **Совет SideFX «вычисляйте парм, а не строку» нельзя применять слепо.**
    Из 115 ссылок сцены 38 разрешаются ТОЛЬКО через `expandString` и ни одна —
    только через `evalAsString()`. Эти 38 — FBX: парм отдаёт
    `airship_v06.fbx#Airship_fullBindings,convertoff`, адрес ВНУТРЬ файла, а не
    путь на диске. Правило: пробовать оба способа, брать то, что существует;
    существуют оба и различаются — брать оба.

- **Заливается не «всё, на что ссылается сцена», а то, что нужно этому куку
  (Ruling R38).** `hou.fileReferences()` отвечает на вопрос «в каких пармах
  лежат пути», а не «что сцене нужно прочитать, чтобы отрендериться». Замер на
  живой сцене владельца (`airship_v013.hip`, 2026-09-05): нода планировала
  **795 файлов / 10.0 ГБ** там, где ветвь читает **78 файлов / 1.2 ГБ**.

  **Один парм давал почти всю разницу:** `pdg_workingdir` у
  `/stage/lookdev_pdg/localscheduler` — рабочий каталог ЧУЖОГО шедулера,
  указывавший на папку проекта. Ссылка на директорию раскрывается рекурсивно,
  и внутрь уехали десять версий .hip, 467 готовых EXR и zip на 1.47 ГБ.
  Рабочий каталог шедулера не является зависимостью ничего.

  Три следствия, и они независимы:

  * **Пармы вывода не зависимости — в обоих скоупах.** Список имён
    (`rpfarm.deps._NON_DEPENDENCY_PARMS`): `pdg_workingdir`, `outputimage`,
    `savetodirectory_directory`, крипто-сайдкары, `taskgraphfile` и прочие.
    Отбор по ИМЕНИ парма, а не по паре (тип, парм): имя значит одно и то же на
    всех типах, где встречается, а таблица типов протухнет на следующей версии
    HDA. Тег `filechooser_mode` для этого не годится — проверено на живой
    сцене: у 20 из 21 группы ссылок его просто нет, а у `file`/`file` (File SOP,
    настоящая зависимость) он `read_and_write`. Один этот фильтр: 10.0 ГБ → 1.6 ГБ.
  * **Скоуп «ветвь» — дефолт.** От каждой ROP Fetch в этой TOP-сети к её
    `roppath` и вверх: входные предки, парм-ссылки на ноды
    (`hou.stringParmType.NodeReference` — так LOP достаёт SOP через `soppath`,
    без провода) и содержимое каждой достигнутой ноды. 1.6 ГБ → 1.2 ГБ. Если
    ветвь не определяется (в сети нет ни одной ROP Fetch) — откат на всю сцену
    с записью в лог: сузить не удалось значит грузим всё, а не ничего.
  * **Честный предел метода, записанный в подсказке парма:** ассеты, на которые
    USD-слой ссылается ИЗНУТРИ себя, в `hou.fileReferences()` не видны вообще.
    Сужение их не теряет — их там и не было. «Whole scene» от этого не спасает.

  **Ссылка на директорию — опасная операция, и молча её разворачивать нельзя.**
  Один парм даёт неограниченный объём. Поэтому окно подтверждения показывает
  директорию ОДНОЙ строкой с полным рекурсивным весом (а не 827 строками), список
  отсортирован по весу вниз, а снятые галочки живут на ноде (`rpfarm_exclude`),
  чтобы окно не превращалось в налог на каждый кук. Когда окна нет (батч, hython,
  генерация не в главном потоке) каждая директория всё равно логируется с полным
  весом — «не молча» выполняется в обе стороны.

  **Окно никогда не является причиной, по которой сабмит не состоялся.** Отмена
  — это осознанное «нет», кук останавливается. А вот отказ самого Qt (нет
  QApplication, генерация в другом потоке) логируется и заливка идёт по
  запомненному выбору. Qt из не-главного потока — не исключение, а потерянная
  сессия, поэтому поток проверяется до, а не после.

- **Жизненный цикл sync-пода: сперва остановить, потом удалить; исполнитель —
  только Houdini (Ruling R36).** Решение владельца. Оба порога — параметры ноды
  (`Stop Sync Pod After`, `Delete Stopped Sync Pod After`) по обычной конвенции
  «значение конфига видно в поле». Остановленный под сохраняет контейнерный
  диск и поднимается за секунды, но **стоит не ноль**: RunPod берёт за диск
  остановленного пода вдвое против работающего ($0.20 против $0.10 за ГБ/мес),
  то есть ~$2/мес против ~$43/мес работающим — отсюда второй порог.

  **Ключ на под не кладём, поэтому сторож из task-18 закрыт этим решением.**
  Из этого следует честное ограничение, записанное прямо в подсказках
  параметров: закрытый или упавший Houdini не погасит ничего. Смягчено тем,
  что проверка идёт не только в `onSetupCook` (именно поэтому под однажды
  провисел часами — между куками никто не смотрел), но и по таймеру сессии
  раз в минуту, плюс `atexit` как любезность, а не гарантия. Оставшийся под
  виден в Farm Status ноды, а не только в панели RunPod.

  **Ловушка, которую нельзя воспроизвести:** `_find_or_create_sync_pod` раньше
  ТЕРМИНИРОВАЛ любой не-RUNNING под и создавал новый. Пока никто ничего не
  останавливал — безвредно; с этим решением это означало бы платить за
  остановленный под и за его замену одновременно, выбросив тот самый диск,
  ради которого под и останавливали. Теперь любой не-RUNNING под предлагается
  `start_pod`, и только отказавшийся вернуться терминируется. На точное
  значение `desiredStatus` остановленного пода код не опирается — проверить
  его, не остановив под, нельзя.

- **Живость пода измеряется по всем каналам, а не только по HTTP (Ruling R34).**
  `/health` считал только запросы к воркеру, поэтому под, которым управляют
  по SSH, отчитывался `busy 0` и растущим `idle_s`, пока рендерил: бенчмарк-под
  отдал 15 кадров и всё это время выглядел брошенным, а `classify_for_kill`
  разрешал его гасить. Производственный случай хуже диагностического: rclone
  везёт файлы на sync-под по SFTP, поэтому под, принимающий четырёхгигабайтный
  тарбол Houdini — самую тяжёлую работу, какую ферма вообще делает, — выглядел
  простаивающим ровно в этот момент. Сторож из task-18 в таком виде убил бы его
  посреди передачи.

  Поэтому `/health` отдаёт ещё два факта: `ssh_sessions` (установленные
  соединения на порт 22) и `transfers` (процессы `rclone`/`sftp-server`/
  `rsync`/`scp`). Оба читаются из `/proc` напрямую — в тонком образе нет ни
  `ss`, ни `lsof`.

  **Признаки дискретные, а не пороговые, и это осознанный выбор.** Порог по CPU
  пришлось бы калибровать против собственного фонового шума пода, то есть его
  нельзя выбрать без живой машины; наличие соединения или процесса калибровки
  не требует и не дрейфует.

  **Ошибка допускается только в сторону «занят».** Под, который не сообщил эти
  поля (старый образ, недостижимый воркер), классифицируется `unknown`, а не
  `safe`: ложное «занят» стоит центов простоя, ложное «свободен» стоит чужого
  рендера или оборванной передачи — второе у нас уже случалось.

  **Полевая проверка на живом sync-поде во время реальной заливки владельца
  вскрыла, что первая реализация была неверна в ОБЕ стороны, и оба признака
  по отдельности недостаточны:**

  * `transfers` считал одиннадцать процессов `sftp-server`, **все `<defunct>`**,
    перевешенные на PID 1 — заливка к тому моменту уже закончилась. То есть
    признак показывал «занят» не потому, что работа шла, а потому, что трупы
    не пожали. Это хуже исходного бага: под, залипший в «занят» навсегда,
    `farm kill` не расчистит уже никогда. Зомби теперь исключаются по состоянию
    `Z` в `/proc/<pid>/stat`.
  * `ssh_sessions` при этом честно показывал 0, и это была правда:
    в `/proc/net/tcp` на том поде висела только строка LISTEN для `:0016`.
    rclone открывает и закрывает соединение **на каждый файл**, поэтому
    посреди заливки существуют мгновения без единого установленного сокета и
    без единого живого потомка.

  Второе полевое наблюдение (владелец отменил кук посреди заливки) добавило
  третий урок: **исключить зомби было мало**. Живой `sftp-server`, держащий
  открытое соединение и ничего не делающий, — это присутствие, а не работа, и
  считать его «занят» так же залипает, как считать трупы, только фитиль длиннее.
  Поэтому работой считается ДВИЖЕНИЕ БАЙТ: `sample()` берёт сумму
  `read_bytes`+`write_bytes` живых процессов передачи из `/proc/<pid>/io` и
  сравнивает с предыдущим замером. Открытое соединение по-прежнему считается
  занятостью само по себе — вошедший человек присутствует и между файлами.

  Отсюда правило: **мгновенный замер — не доказательство, а наличие процесса —
  не работа**. Воркер сэмплирует раз в 2 с фоновым потоком и отдаёт
  `busy_idle_s` — сколько прошло с момента, когда работа действительно шла.
  Судить нужно по нему; `transfers` и `ssh_sessions` остаются сырыми фактами
  для диагностики.

  **Вечное «занят» — не безопасная сторона, а отказ автоматики.** Асимметрия
  «ошибаться в сторону занят» относится к одному решению, а не к бесконечному:
  под, который навсегда «занят», политика остановки никогда не остановит и
  `kill --all` не возьмёт. Оба поймавшихся случая (зомби, живой-но-простаивающий)
  были именно такими.

- **PID 1 в контейнере обязан пожинать сирот (Ruling R37).** `entrypoint.sh`
  заканчивается `exec python3 worker.py`, то есть PID 1 был воркером. Когда
  сессионный процесс sshd умирает, его потомок `sftp-server` перевешивается на
  PID 1 — а Python-PID 1 никогда не делает `wait()` на усыновлённых, поэтому
  каждая завершённая SFTP-сессия оставляла `<defunct>` навсегда. Наблюдалось на
  живом sync-поде: одиннадцать после одной заливки плюс два осиротевших sshd.
  Лечится `tini` в качестве PID 1 — он пробрасывает сигналы и пожинает то, что
  унаследовал, не вмешиваясь в то, как воркер ждёт СВОИХ детей. Обработчик
  `SIGCHLD` внутри воркера был бы неверным инструментом: он гонялся бы с
  `subprocess` за кодами возврата задач.

  **Следствие для вопроса «держит ли RunPod своё SSH-соединение»:** ноль,
  снятый со сломанного счётчика, не значил ничего. Вопрос открыт до повторного
  замера на исправленной сборке.

- **Межподовые сравнения производительности ничего не значат (Ruling R35).**
  Один и тот же кадр этой сцены измерился в 35.7 с на одном поде и ~78 с на
  другом — оба RTX 4090. Любой замер имеет смысл только back-to-back на одной
  машине, в одном прогоне. Именно из-за нарушения этого правила XPU сначала
  объявили в 1.4 раза медленнее CPU, тогда как на самом деле он в 1.79 раза
  быстрее (холодный XPU сравнили с тёплым CPU).

- **Гашение пода требует доказательства, что он свой и простаивает (Ruling R33).**
  Аккаунт общий. Агент, который видел только своё состояние, решил, что любой
  работающий под — его остаток, и погасил чужие: через 36 секунд после того, как
  чужой кук успел закончиться. Минутой раньше это был бы уничтоженный рендер с
  восемью GPU-минутами внутри. Дисциплина «сверяйся перед гашением» — слабая
  защита, поэтому дефолт сделан неспособным на это.

  * **Личность пода живёт на самом поде.** `pod_env` кладёт `RPFARM_USER`,
    `RPFARM_COOK`, `RPFARM_PROJECT`; RunPod отдаёт `env` в `GET /pods`, значит
    «чей это под и к какому куку относится» отвечается снаружи, без локального
    состояния той машины, которая его создала. Имя (`rpfarm-<user>-<project>-
    <cook>-<n>`) остаётся для людей: разбирать его нельзя, юзер или проект с
    дефисом делают разбор неоднозначным.
  * **Живость кука — два числа из `/health` пода:** `busy` (сколько задач
    выполняется) и `idle_s` (сколько прошло с последнего НЕ-`/health` запроса).
    Одного `busy` мало: между двумя задачами живого кука он на секунды падает в
    ноль, и этот момент не должен читаться как «брошен». `/health` намеренно не
    обновляет `idle_s` — иначе сам вопрос «ты простаиваешь?» делал бы ответ
    отрицательным, а сторож задачи 18 держал бы брошенный под вечно живым.
  * **`classify_for_kill`** даёт `safe` / `busy` / `foreign` / `unknown`.
    Гасится только `safe`. Владение проверяется раньше живости: чужой
    простаивающий под — всё равно не наш. Недостижимый под — `unknown`, и
    незнание разрешается в «не трогать»: цена ожидания это центы, цена ошибки
    это чужой рендер.
  * **Снести живое или чужое можно только явным намерением:**
    `--even-if-running` и `--everyone`, каждый с подтверждением (`--yes` для
    скриптов). Ни один не подразумевается другим. `--pod <id>` подчиняется тем
    же правилам.

  Это тот же механизм, который нужен сторожу простаивающих подов (task-18):
  он смотрит на те же `busy` и `idle_s`, только локально и чтобы погасить себя.
  Сделан один раз, в `/health`.

- Лицензии: `doctor` проверяет `lic.ai-vfx.com:1715`; задача с ошибкой лицензии в логе
  не ретраится, шедулер останавливает кук с понятным сообщением.
- Баланс RunPod ниже порога (параметр): предупреждение перед куком.
- Секреты: только `~/.rpfarm/config.toml` (chmod 600) и env подов; в репо — имена.
  Старый шаблон `4tee2rtpu4` с паролем Redis в env удаляется.

## 8. Тестирование

- Юнит (pytest, без Houdini): `deps` (на фикстурах путей), `sync` (планировщик пакетов,
  files-from), `ledger` (записи, сшивка с биллингом), `runpod_api` (моки HTTP),
  `worker.py` (локальный запуск, задачи, kill).
- Интеграция `rpfarm smoke`: поднять sync-под → залить тестовый хип (3 кадра, Karma CPU
  и один GPU-кадр) → шедулер поднимает 1 GPU-под → кадры приходят в локальный путь →
  поды погашены → в журнале и биллинге видны записи. Критерий готовности проекта.
- Ручная проверка на реальном шоте 5–50 ГБ: время заливки, инкрементальность второго
  кука, скачивание по мере рендера.
