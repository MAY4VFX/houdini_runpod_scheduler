# RunPodFarm — покрытие скоупа и цельность пользовательского flow

Дата: 2026-09-10. Срез: `b93ce1c` + существующие незакоммиченные изменения R71.

Базовый v2 выпущен. Расширенный сценарий автономной отправки пока не завершён. Основной UX-долг — несколько независимых владельцев настроек, доставки и статуса одной работы. Перестановка вкладок без исправления этих связей проблему не решит.

## Основание и границы аудита

- Свежий GitHub: [MAY4VFX/houdini_runpod_scheduler#1 «RunPodFarm v2: sync-под + rclone/sftp + MQ на ферме, без Redis/B2/сервера»](https://github.com/MAY4VFX/houdini_runpod_scheduler/issues/1) закрыт, Project = Done. Комментарий 4 сентября подтверждает сквозной рендер и миграцию. Это завершённый базовый scope; переоткрывать его по состоянию сегодняшней рабочей папки оснований нет.
- Прочитаны исходная цель/план, актуальные дополнения спецификации, HDA definitions/builders, scheduler, upload/download runner, host launcher, status, housekeeping, stats и настройки.
- `python3 -m pytest -q`: **1205 passed, 2 failed, 2 skipped, 81.93 s**. Среди проверок — создание HDA в отдельном Houdini с изолированными prefs; рабочая сцена пользователя не использовалась.
- Отдельным локальным harness воспроизведена потеря текущего статуса при вызове настоящего `_showSyncPodBetweenCooks` с подставленным интерфейсом `hou`.
- Ранее в этой сессии на живом sync-поде воспроизведено: локальный token → HTTP 401 и timeout; token пода → health/ready успешно. Повторный cook пользователя этим аудитом не проверялся.
- Текущее окно Houdini не инспектировалось: доступ Computer Use не предоставлен. Визуальная оценка основана на DialogScript/callbacks и исходном скриншоте, не на полном просмотре интерфейса в работающей сцене.
- Новые облачные поды, transfer/cook, установки, изменения кода и GitHub этим аудитом не выполнялись. Добавлены только два документа аудита.
- Сопоставление с официальной моделью SideFX: [Houdini UX reference review](2026-09-10-houdini-ux-reference-review.md).

## Покрытие функционального скоупа

| Область | Что реализовано | Оценка готовности |
|---|---|---|
| Основа v2, миграция v1 | REST API, CPU sync, GPU workers, общий volume, MQ, CLI setup/doctor, удаление старого серверного стека | Базовый scope закрыт и подтверждён трекером |
| Зависимости и upload | Сбор зависимостей, branch scope, USD/OCIO/env paths, preview/exclusions, пакеты, сравнение файлов, компрессия, отдельные процессы | Реализовано; состояние подготовки и ошибки доступа представлены недостаточно ясно |
| Рендер/симуляционные задачи | PDG dispatch, MQ/batch callbacks, GPU selection, scaling/retry/capacity wait, path mapping | Реализовано; этот аудит не подтверждает заново живые аварийные/multi-pod сценарии |
| Получение результатов | Автоскачивание scheduler + Download TOP, custom paths, overwrite | Реализовано двумя независимыми путями; локальные outputs Download не зарегистрированы в PDG |
| Учёт и storage | Ledger, billing merge, Stats/CSV, volume browser, grow/prune/recreate через UI/CLI в разных сочетаниях | Основные механизмы есть; представление и обновление данных раздроблены |
| Жизненный цикл | Cleanup GPU в cook, повтор termination, sync stop/delete, таймер открытой UI-сессии | Частично автономно: закрытый/упавший Houdini не исполняет session timer; автономный sync-watchdog остаётся отдельным незавершённым scope |
| Локальный Background Cook | Запуск отдельного hython, сохранение сцены, лог | Запуск есть; нет постоянной привязки job к сцене с monitor/reconnect/cancel |
| Submit As Job после локального upload | В рабочей версии добавлены явный target, local upload, serialize состояния; ранее реализованы host credentials и self-termination | В работе: producer состояния добавлен, новый executor ещё не подключён |
| Возврат после выключения компьютера | Спецификация требует обычный Cook Download в новой Houdini-сессии с восстановлением отправленного состояния | Не реализован полный путь: Download пока читает только текущие upstream resultData/custom paths |
| Доставка версии пользователю | Изолированная установленная копия `~/.rpfarm/pkg`, guards, сборка HDA | Механизм существует, текущий checkout не готов к установке: 2 упавших проверки |
| Документация текущего продукта | План, большой журнал решений в spec, README | Несогласована по времени: README повторяет уже исправленные ограничения; заголовок spec всё ещё «ждёт план реализации» |

Процент готовности здесь был бы ложной точностью: наличие большинства модулей не закрывает один отсутствующий обязательный переход между сессиями.

## Подтверждённые пробелы и последствия

### P0. Автономный сценарий не замкнут

Последняя постановка R71: Submit → upload локально → выключить компьютер → открыть новую Houdini-сессию → Cook Download → получить кадры без нового рендера.

На текущем срезе:

1. Scheduler пишет `taskgraph_in.bin` в staging: `hda/runpodfarm_scheduler.hda/Top_1runpodfarmscheduler/PythonModule:4078`.
2. Новый `pod/host_render.py` умеет deserialize/cook/serialize, но остаётся untracked.
3. `pod/host_cook.py:280`–`:289` продолжает запускать `topcook.py`; новый executor не вызывается.
4. `pod/Dockerfile:72` копирует host_cook, но не host_render.
5. Download generator в `scripts/build_runpodfarm_download_hda.py:205` использует текущие upstream `resultData`; поиска отправленного job, получения `taskgraph_out.bin` и `deserializeWorkItems` в нём нет.

Это незавершённый рабочий diff другого агента, а не доказательство регрессии уже установленной версии. Одного успешного запуска host-пода для приёмки недостаточно.

### P0. Текущий checkout не является согласованной сборкой

Упали:

- `tests/test_hda_assets.py::test_every_shipped_asset_was_built_against_this_package` — fingerprint устарел в scheduler и builders upload/stats.
- `tests/test_node_creation.py::test_every_farm_node_can_actually_be_created` — PythonModule scheduler не загружается из-за несовпадения `pods.py`; класс scheduler недоступен.

Guard советует «ПЕРЕЗАПУСТИТЕ HOUDINI. Больше ничего делать не нужно», хотя проверка уже выполнена в НОВОМ процессе. Здесь требуется согласованная сборка, а не restart. Не устанавливать рабочий diff поверх активной сессии ради исправления этого аудита.

Установленный пакет на момент диагностики был от 9 сентября; текущие изменения репозитория от 10 сентября в него целиком не доставлены. Состояния «написано», «собрано», «установлено», «загружено в сессию» нельзя считать одним.

### P1. Доставка имеет двух владельцев и не является отдельным наблюдаемым результатом

Scheduler `Download Outputs` и Download TOP планируют одни файлы независимо. Проверка в `scripts/build_runpodfarm_download_hda.py:262` выдаёт warning, но сохраняет повторный проход. Совпадающие файлы rclone может пропустить, поэтому утверждение «каждый байт обязательно передаётся дважды» неверно; лишний проход/листинг/получение sync-пода остаётся.

У scheduler `_settleResults` сначала отмечает work item успешным, затем ставит скачивание в очередь (`PythonModule:2338`). `_drain_sync_queue` выполняет transfer синхронно и вызывается из `onTick` до следующего обновления бюджета/статуса (`:2343`, `:3378`). Параметр `block=False` ограничивает число пакетов, но не превращает передачу одного пакета в асинхронную операцию. Продолжительность задержки требует отдельного замера.

Download runner заканчивается счётчиками и exit 0, не сообщает новые локальные файлы через PDG Output files (`rpfarm/package_runner.py:188`). Поэтому «рендер завершён», «файл на ферме», «файл доставлен» не имеют полноценного общего представления. В downstream невозможно надёжно опираться только на зелёный render item как доказательство доставки.

### P1. Project и farm config могут расходиться между стадиями

Upload читает собственный Project (`scripts/build_runpodfarm_upload_hda.py:465`), scheduler — свой (`PythonModule:2721`). `scene_setup.py:244`–`:245` только задаёт одинаковые начальные значения, не связывает параметры.

Scheduler позволяет overrides API key/volume/template/datacenter; transfer runner читает `config.toml`. `_node_config` для management callbacks подменяет API client key, но возвращает исходный cfg (`PythonModule:678`). В итоге изменение параметра scheduler не обязано менять место загрузки или объект, показываемый управлением томом.

Нужен один resolved farm context, который все стадии получают от выбранного scheduler, с явно показанными локальным корнем, project и remote root. Локальные overrides должны быть явными и последовательно передаваться.

### P1. Статус теряется и маскирует реальные причины

- `WorkerClient._json` возвращает `None` для любого не-200; `wait_ready` превращает 401 в пять минут ожидания. Это подтверждено живым differential probe, а не только чтением кода.
- До transfer callback нет явной phase (`package_runner.py:138`–`:153`). Пользователь не различает ожидание CPU, старт воркера, проверку доступа и передачу.
- `_update_status_text` начинает строку с `РЕЖИМ:` (`PythonModule:2499`), а `_showSyncPodBetweenCooks` защищает активный статус только по `startswith("cook ")` (`:538`).

Последний дефект воспроизведён выполнением настоящей `_showSyncPodBetweenCooks` с fake `hou` и строкой, соответствующей текущему writer:

```text
active cook status preserved: False
new value: sync pod test-sync RUNNING  about 0.060 USD/h
(housekeeping runs while Houdini is open)
AssertionError: Active cook status was overwritten by sync housekeeping
```

То есть потеря сведений о задачах/стоимости — конкретный дефект двух писателей одного поля. Исправлять надо ownership состояния, а не только оформление поля.

### P1. Автономный job не имеет постоянной точки наблюдения

Background Cook отдаёт одноразовое сообщение с PID/log (`PythonModule:4347`). Submit возвращает URL пода и сбрасывает локальное cook state (`:4227`–`:4254`). Есть удалённые/локальные логи и ledger, но нет законченного пользовательского пути восстановления привязки к выбранной отправке.

Нужна сохраняемая ссылка на конкретный cook/job: target, состояние, время, outputs, лог. Тогда повторный Cook Download работает с выбранной отправкой, а Cancel относится к ней. Под — исполнитель, его URL не заменяет идентичность задачи после удаления пода.

### P2. UI смешивает работу, обслуживание и объяснения реализации

- Cook, Background Cook и Submit используют разные target semantics. Само существование native Cook/Submit корректно; несогласован их пользовательский контракт.
- `Kill All Pods` исключает sync, рядом `Stop Everything, Sync Pod Too`; это не эквивалент стандартного Cancel Cook и названия плохо выражают scope.
- `Manage Volume` и ручной `Target`/`Delete Target` дублируют управление выбором объектов.
- `Sync Ledger`, Stats Refresh и Volume Refresh обновляют разные представления без общей отметки актуальности. Stats Refresh может запросить/создать sync-под; это не только перерисовка локальной таблицы.
- Длинные disabled strings используются как help и dashboard. Текст Background Cook противоречит нынешнему Submit; в tooltip `Use Output Node` видны Ruling R71 и история шести аренд.
- Budget и live cost в scheduler считаются по GPU dispatcher (`PythonModule:2381`), без sync/host/storage. Нужна честная подпись области бюджета/оценки, а не впечатление потолка всего счёта.

## Предлагаемый единый flow

Это проектное предложение, не уже реализованное поведение и не новое требование SideFX.

```text
Один выбранный farm scheduler / project context
                   │
     Upload → Gate → Render → Download
                   │
       один cook/job и его результаты
```

- **Upload** отвечает за данные, исключения и видимый прогресс отправки.
- **Scheduler** отвечает за ресурсы, dispatch, выбранный режим исполнения и бюджет. Физическая реализация transfer может быть общей библиотекой, но пользовательская стадия доставки имеет одного владельца.
- **Render** остаётся обычным ROP Fetch и обычными PDG items.
- **Download** отвечает за локализацию результатов и регистрирует локальные outputs. Для работы «сейчас» получает готовые результаты в том же flow; для «забрать позже» сначала восстанавливает состояние выбранного отправленного cook. Конкретную механику PDG generation/cache при таком восстановлении нужно проверить интеграционно.
- **Stats** можно сохранить как TOP для аналитики. Само наличие четырёх типов нод не является дублем; дублируется ответственность между ними.

Обычный Cook и автономный Submit остаются штатными понятиями Houdini. Для автономного режима достаточно одного согласованного выбора места управляющего процесса: локальный фон / ферма. Target и граница local upload → remote render видимы заранее; не нужно добавлять новую кнопку «восстановить» перед стандартным Cook Download.

Одна модель результатов показывает отдельно: ожидается → готов на ферме → доставлен локально → отсутствует/ошибка. Одна модель исполнения показывает подготовку, очередь ресурса, render, transfer и актуальность данных. Прогресс и файлы доступны в Task Graph Table/work item info; подробности ошибки — через штатные node warnings/errors и log. Общая краткая сводка на scheduler дополняет эти механизмы.

Официальное основание: [Cook и Submit Graph As Job](https://www.sidefx.com/docs/houdini/tops/cooking.html), [TOP UI / Task Graph Table](https://www.sidefx.com/docs/houdini/tops/ui.html), [Job API / output files](https://www.sidefx.com/docs/houdini/tops/jobapi.html). Remote graph monitoring — возможный вариант, его сетевую применимость к этой ферме аудит не подтвердил.

## Порядок завершения

1. **Замкнуть R71 и собрать согласованную версию.** Подключить host executor, сохранение/выбор job, возврат состояния в новый Download cook. Приёмка — две отдельные сессии без повторного upload/render на ферме и без зависимости от первой машины.
2. **Один контекст и одна доставка.** Устранить независимые Project/config overrides и второй retrieval pipeline. Проверять outputs как реальные локальные файлы; не удалять remote результаты до подтверждённой доставки нужного cook.
3. **Правдивое состояние и восстановление.** Отдельные ошибки авторизации/сети/старта, phase/progress, постоянная привязка job, ownership Status, понятная область Cancel/Stop и учёта стоимости.
4. **Упростить поверхность.** Согласовать launch target, объединить дубли management/refresh, убрать историю разработки из help, обновить scene builder и документацию под окончательный flow.

Не входят автоматически: новый веб-dashboard, сервер управления, S3 upload, отдельные volumes и универсальный рефакторинг всех модулей. Эти пункты не нужны для исправления найденных UX-разрывов.

## Минимальная приёмочная матрица

| Сценарий | Что должно быть видно и доказано |
|---|---|
| Первый обычный cook | Upload/Render/Download имеют понятные состояния; кадр доступен как локальный PDG output |
| Повторный cook без изменений | Нет лишнего render и второго retrieval; виден cache/skip |
| Изменение Project или farm override | Все стадии используют один новый context; preview показывает фактическую цель |
| Неверный sync token | Немедленная явная ошибка доступа, без пяти минут «под запускается» |
| Нет capacity | Видны причина ожидания и истекающий срок; Cancel прекращает ожидание |
| Автономная отправка | После закрытия первой сессии job продолжает работать и идентифицируется независимо от pod |
| Download в новой сессии | Восстанавливается нужный cook; нет нового render; проверены локальные outputs |
| Ошибка/отмена скачивания | Render success не выдаётся за delivery success; данные на ферме доступны для повторного получения |
| Статус во время cook и после | Sync timer не затирает cook; видны актуальность, итог и оставшиеся оплачиваемые ресурсы |
| Установка релиза | Fresh-Houdini node creation и fingerprint проверки проходят; текущая сцена не получает смесь версий |

Все пункты выше — предложения для приёмки будущих изменений, а не утверждение, что они пройдены текущим аудитом.

## Дополнение владельца и backlog (10 сентября)

После согласования аудита владелец добавил требования:

- Показать логику упаковки файлов в work items, состав каждого пакета и ход передачи с оставшимся объёмом/временем. 106 файлов суммарно 1,37 GiB могут быть одним item при лимите 1,5 GiB; это должно быть видно до старта.
- Объединить preflight в один workflow с двумя деревьями Local / Farm и зелёной подсветкой совпадений, дополняющей текстовое состояние.
- Выбирать файлы и удалять их прямо в этом окне, с явным различием сторон и отдельным подтверждением удаления.
- Сохранить автооткрытие перед cook. Ручной просмотр должен сохранять выбор, а не называться Upload, когда ничего не отправляется.
