# RunPodFarm v2 (`rpfarm`)

Рендер-ферма для Houdini на RunPod: артист жмёт **Cook** в TOP-сети, зависимости
хипа уезжают на ферму, поднимаются GPU-поды, кадры считаются и приходят обратно
**ровно в те локальные пути, на которые были нацелены ROP-ноды**, поды гаснут.
Своих серверов, VPN и консолей не нужно — только аккаунт RunPod и Houdini.

Интерфейсов ровно два: четыре TOP-ноды в Houdini и CLI `rpfarm`.

Дизайн: [`docs/superpowers/specs/2026-09-02-rpfarm-v2-design.md`](docs/superpowers/specs/2026-09-02-rpfarm-v2-design.md).
План реализации: [`docs/superpowers/plans/2026-09-02-rpfarm-v2.md`](docs/superpowers/plans/2026-09-02-rpfarm-v2.md).

## Быстрый старт

Что нужно заранее:

* **Python 3.11+** в системе (не hython — CLI работает на обычном питоне).
* **Houdini 22.0** локально, запущенный хотя бы раз (нужен каталог настроек).
* **Аккаунт RunPod** с положительным балансом и API-ключом
  (RunPod Console → Settings → API Keys).
* **Сервер лицензий SideFX**, доступный подам по TCP. У этой фермы —
  `lic.ai-vfx.com:1715`; свой адрес пропишите в `~/.rpfarm/config.toml`
  (`sesinetd_host` / `sesinetd_port`). Без него `hython` на поде не запустится.
* **Тарболл Houdini под Linux** (`houdini-22.0.393-linux_x86_64_gcc14.2.tar.gz`)
  — если Houdini на волюм фермы ещё не ставили.

```bash
# v2 пока живёт в своей ветке; после мержа берите main
git clone -b v2 https://github.com/MAY4VFX/houdini_runpod_scheduler
cd houdini_runpod_scheduler

python3 -m rpfarm setup      # спросит ключ RunPod; всё остальное — сам
python3 -m rpfarm doctor     # проверка по пунктам; подов не поднимает и денег не тратит
```

`setup` идемпотентен: его можно запускать сколько угодно раз, он не затирает
руками выставленные поля конфига. Он создаёт `~/.rpfarm/` (`config.toml` c
chmod 600, токен воркеров, SSH-ключ), скачивает `rclone`, находит/создаёт
network volume и шаблон пода, собирает четыре HDA (`hotl -l`) и кладёт их в
`<prefs>/otls/`.

Дальше — Houdini на волюме фермы (один раз на volume, ~10 ГБ, несколько минут).
Первую из этих двух команд стоит выполнять с открытыми глазами: она проверена
живьём один раз, при миграции на Houdini 22 (Task 14), и с тех пор не
повторялась — см. колонку «проверено» в разделе [«Команды»](#команды). Вторая
гоняется регулярно.

```bash
python3 -m rpfarm houdini install \
    --tar ~/Downloads/houdini-22.0.393-linux_x86_64_gcc14.2.tar.gz \
    --version 22.0.393
python3 -m rpfarm houdini ls
```

Если Houdini на волюме уже стоит (`houdini ls` показывает версию) — этот шаг
пропускается.

Проверка всей цепочки одной командой — она поднимает поды, считает три кадра
Karma CPU и гасит всё за собой (см. [«Сквозной тест»](#сквозной-тест)):

```bash
python3 -m rpfarm smoke
```

### Первый кук из Houdini

1. Откройте сцену, убедитесь, что `$JOB` указывает на папку проекта
   (всё, что лежит под `$JOB`, уезжает на ферму с сохранением структуры).
2. Создайте `topnet`, внутри него — **RunPodFarm Scheduler**, и назначьте его
   планировщиком сети (`TOP Scheduler` на самом topnet).
3. Соберите цепочку:

   ```
   RunPodFarm Upload  (Mode: Project Dependencies)
        │
        ▼
   Wait For All        ← обязательно, см. ниже
        │
        ▼
   ROP Fetch          (ваш Karma / Mantra / File Cache ROP)
        │
        ▼
   RunPodFarm Download (Mode: Upstream Outputs)
   ```

4. Нажмите **Cook** на **самой нижней** ноде — на `RunPodFarm Download`.

> **Зачем `Wait For All` после Upload.** Upload делает **один work item на
> пакет**, а пакетов бывает больше одного: файлы бьются и по размеру
> (`Package Size`, по умолчанию 1.5 ГБ), и по корню — всё, что лежит вне
> `$JOB`, уезжает отдельной группой в `_ext/`. Любая нода ниже генерирует свои
> айтемы **на каждый входящий**, так что без партишенера сцена из двух пакетов
> даёт `ROP Fetch` 2 × N айтемов и рендерит каждый кадр дважды (ровно это и
> случилось в первом живом прогоне: 6 рендеров вместо 3). `Wait For All` схлопывает пакеты в
> одну партицию — и рендер планируется один раз, сколько бы пакетов ни
> получилось. Партишенеры и `merge` не несут команды и до планировщика фермы
> вообще не доходят (PDG разрешает их сам), так что на ферме это бесплатно.

> **Кукать нужно ровно одну, самую нижнюю ноду, одним вызовом.** Если кукнуть
> сначала ROP Fetch, а потом отдельно Download, PDG запустит два независимых
> кука и оплатит **второй GPU-под**. Это единственная неочевидная вещь во всём
> UI; она же написана в Help обеих нод.

Четвёртая нода, **RunPodFarm Stats**, ни от чего не зависит и ни во что не
включается — это отдельный topnet для аналитики (см. «Стоимость и чистка»).

Пример готового графа лежит в репозитории:
[`tests/fixtures/smoke/smoke.hip`](tests/fixtures/smoke/smoke.hip) — сфера,
камера 320×240, Karma CPU на три кадра, Scheduler + Upload + Download.
Пересобирается
скриптом `scripts/build_smoke_fixture.py` (см. его докстринг: там объяснено,
почему в путях вывода `$HIP`, а не `$JOB`).

## Как это работает

```
машина артиста                                RunPod (EU-RO-1)
┌───────────────────────────────┐            ┌──────────────────────────────────┐
│ RunPodFarm Upload    (TOP) ───┼─ sftp ────►│ sync-под (CPU, ~$0.06/ч)         │
│ RunPodFarm Scheduler (TOP) ───┼─ HTTPS ───►│  sshd · rclone · worker.py       │
│    │ PDG MQ клиент ◄──────────┼─ tcp ──────│  mqserver (PDG, hython с волюма) │
│ RunPodFarm Download  (TOP) ◄──┼─ sftp ─────│  housekeeping.py (du/ls/rm)      │
│ RunPodFarm Stats     (TOP)    │            │           │ /workspace           │
│ CLI  python3 -m rpfarm        │            │   Network Volume (один, по зонам)│
└───────────────────────────────┘            │           │ /workspace           │
                                             │ GPU-поды ×N — живут ровно пока   │
                                             │  есть задачи: worker.py, hython, │
                                             │  hserver → lic.ai-vfx.com:1715   │
                                             └──────────────────────────────────┘
```

Что происходит по шагам, когда вы жмёте Cook:

1. **Scheduler** (`onStartCook`) читает `~/.rpfarm/config.toml`, придумывает
   `cook_id`, регистрирует path map `$JOB ↔ /workspace/projects/<user>/<project>`,
   предупреждает о низком балансе и о чужих осиротевших подах.
2. **Upload** собирает зависимости через `hou.fileReferences()` (плюс сам `.hip`),
   бьёт их на пакеты по 1.5 ГБ и заливает `rclone`-ом по sftp на **sync-под** —
   дешёвый CPU-под, который поднимается первым и переиспользуется всеми.
   Пакеты кукаются **вне процесса Houdini**, параллельно: интерфейс не залипает.
3. **Scheduler** поднимает GPU-поды (`gpuTypePriority: custom` — берётся первый
   доступный тип из вашего списка приоритетов, а не самый дорогой), запускает
   `mqserver` на sync-поде и раздаёт задачи подам по HTTP (`worker.py`).
4. Задача на поде — это `hython` с волюма (`/workspace/houdini/<версия>`),
   лицензия берётся с вашего `sesinetd`. Каждый выходной файл ROP сообщает через
   PDG MQ; scheduler **сразу** ставит его в очередь на скачивание, не дожидаясь
   конца кука.
5. **Download** (режим Upstream Outputs) добирает выходы апстрима — тот же путь
   ещё раз, вручную и повторяемо, если что-то нужно перекачать.
6. `onStopCook` гасит все GPU-поды кука, дописывает `cook_summary` в журнал
   `~/.rpfarm/ledger/<cook_id>.jsonl` и зеркалит его на волюм в
   `/workspace/ledger/<user>/`. **Sync-под остаётся жить** — его убирает
   следующий кук по таймауту простоя или `rpfarm farm kill --sync`.

Хранилище — один network volume с зонами:

| Зона | Что лежит | Чистка |
|---|---|---|
| `/workspace/houdini/<ver>/` | установленные Houdini | `rpfarm houdini rm <ver>` |
| `/workspace/apps/` | плагины, дистрибутивы | вручную |
| `/workspace/projects/<user>/<project>/` | зависимости хипов и выходы | `storage rm`, `storage prune` |
| `/workspace/ledger/` | журнал задач и логи подов | ротация boot-логов > 90 дней |
| `/workspace/.rpfarm/` | индекс размеров, служебное | само |

## Команды

Все команды — тонкие обёртки над теми же модулями `rpfarm/`, что использует HDA.
Запуск: `python3 -m rpfarm <команда>` (удобно завести алиас
`alias rpfarm='python3 -m rpfarm'` — дальше в тексте так и написано).

Колонка «проверено» говорит, откуда известно, что команда работает, — чтобы вы
знали, на какие шаги можно опираться, а какие проходите первым:

* **живьём** — запускалась на реальной ферме при написании этой документации
  (2026-09-04), вывод приведён в отчёте задачи; `smoke` вдобавок гоняет всю
  цепочку нод и проверяет результат на каждом запуске;
* **Task 14** — запускалась живьём один раз, при миграции на Houdini 22, и с
  тех пор не повторялась (повтор стоит перезаливки 1.6 ГБ и переустановки);
* **тесты** — покрыта юнит-тестами и гейтами подтверждения, но вживую не
  запускалась: это необратимые операции над общим волюмом, и проверять их
  «для галочки» дороже, чем честно об этом сказать.

| Команда | Что делает | Проверено |
|---|---|---|
| `rpfarm setup` | Конфиг, токен, SSH-ключ, rclone, volume, шаблон пода, установка HDA. Безопасно перезапускать. | живьём |
| `rpfarm doctor` | Проверка всего по пунктам: ключ и баланс, volume, шаблон, лицензионный сервер, rclone, ключ, HDA, Houdini на волюме, скорость аплинка, наличие GPU в стоке. Подов не поднимает: две последние проверки идут только если sync-под уже живой. | живьём |
| `rpfarm houdini install --tar <путь\|sftp://host/path> --version <ver>` | Заливает тарболл на волюм и запускает установщик SideFX. Приёмка — **запуском** `hython` и сверкой версии, а не проверкой файлов. | Task 14 |
| `rpfarm houdini ls` | Версии Houdini на волюме с размерами. | живьём |
| `rpfarm houdini rm <ver> [--yes]` | Удалить версию. Без `--yes` — только показывает, сколько освободится. | тесты |
| `rpfarm storage ls` | Зоны, проекты по пользователям, заполненность волюма. | живьём |
| `rpfarm storage du <путь>` | Размеры детей одного пути на волюме. | живьём |
| `rpfarm storage rm <user>/<project> --force` | Удалить проект. `--force` обязателен: это необратимо. | тесты |
| `rpfarm storage prune [--older-days N] [--yes]` | Проекты, которыми не пользовались N дней (по умолчанию 30). Без `--yes` — сухой прогон. | живьём (сухой прогон) |
| `rpfarm storage grow +N` | Увеличить волюм на N ГБ (RunPod-волюмы только растут). | тесты |
| `rpfarm storage recreate --size N` | Новый волюм нужного размера, конфиг переключается на него; команду удаления старого печатает, но сам не удаляет. | тесты |
| `rpfarm farm status` | Живые поды `rpfarm-*` (всех пользователей аккаунта): тариф, аптайм, накопленная стоимость. | живьём |
| `rpfarm farm kill --all` | Погасить **свои** GPU-поды (не sync, не чужие). | тесты |
| `rpfarm farm kill --sync` | Погасить свой sync-под. | живьём |
| `rpfarm farm kill --pod <id>` | Погасить один под по id. | тесты |
| `rpfarm farm kill --everyone` | **Опасно:** погасить все `rpfarm-*` поды аккаунта, включая чужие. | живьём |
| `rpfarm costs [--by project\|user\|cook] [--since] [--until] [--billing]` | Сводка по журналу; `--billing` подмешивает реальные суммы из биллинга RunPod. | живьём |
| `rpfarm smoke [--gpu ...] [--keep] [--everyone] [--timeout N]` | Сквозной тест, см. ниже. | живьём |

### Сквозной тест

`rpfarm smoke` — единственная проверка, которая гоняет всю цепочку целиком:

```
python3 -m rpfarm smoke
```

Что он делает: копирует `tests/fixtures/smoke/smoke.hip` в `tmp/smoke_<дата>/`,
запускает `hython`, кукает **одну** нижнюю ноду графа, ждёт кадры и проверяет
по факту — три EXR на месте, **свежие** (по mtime, чтобы кадры прошлого прогона
не выдали себя за успех), файл probe-задачи скачан, в журнале есть запись на
каждую задачу с `exit_code 0` и `cook_summary` со стоимостью, а **ваших** подов
на аккаунте не осталось. Любой промах — ненулевой код возврата.

Как выглядит успешный прогон (реальный вывод, 2026-09-04):

```
stage                            detail                   time
-------------------------------  -----------------------  ----
scene load                       smoke.hip                1.7s
upload                           2 item(s), 786.7KB       68s
farm ready                       sync pod + MQ + GPU pod  12s
probe                            1 item(s)                7.2s
render                           3 item(s)                65s
download                         3 item(s)                11s
pod rpfarm-sync-may              $0.060/h                 12s
pod rpfarm-may-smoke-071c3129-1  $0.740/h                 12s
total                            wall clock               201s

cook cost  $0.025   (rpfarm-sync-may $0.060/h, rpfarm-may-smoke-071c3129-1 $0.740/h)
cook id    071c3129
outputs    3 frame(s), 1 probe file(s) in tmp/smoke_20260904-114949
ledger     4 task record(s)

OK: 3 frame(s) rendered on the farm and downloaded to the ROP's own paths in 3m21s
```

У строк `pod …` время значит другое, чем у стадий: сколько прошло от появления
пода в `GET /pods` до появления у него публичного IP. Стоимость — из
`cook_summary`, который пишет сам планировщик, а не оценка теста.

Поды гасятся на **любом** пути выхода, включая падение или таймаут `hython`:
чистку делает родительский процесс, а не сам кук. Чистка **скоуплена на ваши
собственные поды** (`rpfarm-<user>-*` и `rpfarm-sync-<user>`): аккаунт общий, и
smoke не имеет права убить чужой рендер в полёте — чужие поды тест не гасит и не
считает провалом. `--everyone` — явное согласие снести все `rpfarm-*` поды
аккаунта, ровно как у `rpfarm farm kill --everyone`. `--keep` оставляет ферму как
есть (обычное продакшн-поведение, где sync-под живёт дальше) — тогда не забудьте
`rpfarm farm kill --all` (или `--everyone`, если договорились с коллегами).

## Стоимость и чистка

Три источника трат, и все три видно из CLI:

* **GPU-поды** — посекундно, пока идёт кук. Тариф зависит от того, какой GPU
  достался: приоритет берётся из `gpu_priority` в `~/.rpfarm/config.toml` или из
  параметра `GPU Priority` на ноде. Бюджет кука (`Budget ($ per cook)`,
  по умолчанию $5) предупреждает на 80%, перестаёт поднимать поды на 100% и
  гасит всё на 120%.
* **Sync-под** — дешёвый CPU-под (~$0.06/ч), но **он не гаснет сам**
  (см. «Что осталось»). Его снимает следующий кук по `Sync Pod Idle (min)`
  либо вы: `rpfarm farm kill --sync`.
* **Network volume** — платится за **выделенный размер**, а не за занятое место,
  и размер только растёт. Удаление файлов счёт не уменьшает; уменьшить можно
  только через `rpfarm storage recreate --size N` (новый волюм меньшего размера,
  проекты пересинхронизируются при следующем куке — источник правды локальный).

Что смотреть и чем чистить:

```bash
rpfarm farm status                       # что прямо сейчас тикает по деньгам
rpfarm costs --by project --billing      # сколько кто потратил, по биллингу RunPod
rpfarm storage ls                        # заполненность волюма и размер проектов
rpfarm storage prune --older-days 30     # кандидаты на удаление (сухой прогон)
rpfarm storage prune --older-days 30 --yes
rpfarm houdini rm <старая-версия> --yes  # десятки ГБ; вживую не запускалась,
                                         # без --yes показывает план и ничего не трогает
```

Внутри Houdini то же самое даёт нода **RunPodFarm Stats**: work item на задачу,
итоги по проектам и людям, $/кадр, стоимость волюма, кандидаты на чистку с
оценкой $/мес и кнопка экспорта в CSV. Вкладка **Volume** на ноде Scheduler —
браузер волюма с кнопками Delete project / Prune / Grow / Recreate.

Волюм при заливке растёт сам: если пакет переваливает заполнение за 85%, upload
увеличивает волюм так, чтобы после заливки было ~80%, с округлением вверх до
10 ГБ, и пишет об этом в лог ноды и в атрибут work item'а. Проверка никогда не
роняет заливку: если размер волюма выяснить не удалось, она честно пишет
`skipped: ...` вместо того, чтобы гадать.

## Что осталось

Честный список — то, что не сделано, не проверено или лежит на пользователе.

**Требует действий владельца аккаунта**

* Две DNS-записи от v1 остались висеть: `redis-runpod.ai-vfx.com` и
  `db.ai-vfx.com` (обе указывают в никуда — прокси и порты уже сняты). Токен
  Cloudflare, который был под рукой, имеет только `Zone:Read`, поэтому записи
  удаляются вручную в панели.

**Сторож простоя (Task 16)**

* У пода **нет собственного сторожа простоя**. RunPod в API создания пода не
  даёт ни TTL, ни `terminateAfter` (проверено по схеме), а ретайр делает только
  HDA планировщика — и только во время кука. Вне кука sync-под живёт вечно:
  один раз он так простоял ~8 часов и стоил ~$0.50. Пока не появится Task 16
  (вариант: scoped-ключ RunPod с правом только гасить самого себя + вотчдог,
  читающий `/workspace/.rpfarm/sync_last_used`), правило простое —
  **`rpfarm farm status` в конце дня, `rpfarm farm kill --sync`, если под жив**.
* Тот ~8-часовой простой был усилен багом формата метки: путь upload/download
  писал `touch /workspace/.rpfarm/sync_last_used` (пустой файл), а оба читателя
  парсят содержимое как epoch — значит ретайр из HDA не срабатывал никогда.
  Исправлено: единственный писатель — `housekeeping.py sync-touch`, и метка
  обновляется ещё и по ходу длинной передачи, а не только в её конце.

**Границы, о которых надо знать**

* **Отмена кука не сливает очередь скачивания.** Выходы остаются на волюме;
  забрать их — нода `RunPodFarm Download` в режиме `Upstream outputs`. Это
  штатный путь восстановления, а не баг (Ruling R21).
* **`/exec` на поде — только короткие команды**, потолок ~90 секунд: прокси
  RunPod стоит за Cloudflare и рвёт ответ примерно на сотой секунде, а под по
  таймауту убивает всю группу процессов (SIGKILL). Длинные команды (установка
  Houdini, распаковка) идут через отсоединённый путь (`detach: true` + опрос
  статуса). Туда же уехали все разрушающие и «долгие» housekeeping-команды CLI
  — `houdini rm`, `storage rm`, `storage prune`, `storage ls`: удаление 11-ГБ
  дерева не должно получить SIGKILL посреди `shutil.rmtree`. Это уже учтено в
  коде; помнить нужно, если будете дописывать свои post-команды в ноде Upload.
* **Сохранённая сцена морозит внутренности Upload и Download.** Эти две ноды —
  сабнеты, чьи внутренности разблокированы (иначе не задать их внутренний
  планировщик), а разблокированный инстанс HDA сохраняется в `.hip` **вместе со
  своей внутренней сетью**. Значит после `git pull` с обновлёнными HDA ваша
  старая сцена продолжит выполнять старый код — молча. Лечится один раз на
  ноду: правый клик → **Match Current Definition** (параметры на самой ноде при
  этом сохраняются). Фикстура `rpfarm smoke` делает это на сборке, и её
  самопроверка падает, если рассинхрон вернулся.
* **Размер волюма поду неизвестен.** Изнутри пода `statvfs` показывает ёмкость
  бэкенд-пула хоста (на реальном 50-ГБ волюме — ~2.14 PiB), поэтому реальный
  размер всегда передаётся снаружи, из RunPod API. Если увидите `total: null` —
  это не поломка, а честное «не знаю».

**Не проверено живьём** (работает по юнит-тестам и по коду, но реального
прогона не было)

* Автоскейл больше одного пода, ретайр по простою, аварийное гашение по
  бюджету, перевыставление задач при смерти пода, `Submit Graph As Job`.
* **Karma XPU на поде.** Образ намеренно собран без CUDA-рантайма (он стоил
  1.3 ГБ на каждом холодном старте), драйвер инжектит RunPod. CPU-рендер на этом
  проверен, XPU — нет; если XPU потребует `libcuda` из образа, придётся вернуть
  CUDA-базу в `pod/Dockerfile`.
* Windows и Linux как машина артиста: код кроссплатформенный по построению
  (`rclone` под ОС, пути через `posixpath` на удалённой стороне), но гонялось
  только на macOS.

**Известные остаточные риски** (взвешены и оставлены осознанно; подробности —
в докстрингах у соответствующих функций)

* `~/.rpfarm/volume_size_cache.json` читается и пишется без файлового лока.
  Худший исход — лишний вызов `get_volume` к RunPod; неверный размер оттуда
  не приезжает никогда (битое чтение = «нет кеша»).
  См. `rpfarm/packages.py::_volume_size_cache_path`.
* Индекс размеров на поде: мерж-флаш может воскресить ключ, который другой
  процесс инвалидировал во время замера. Исход — устаревший размер не дольше
  `max_age_s`, самоисправляется; на решения об удалении не влияет.
  См. `pod/housekeeping.py::_SizeCache`.
* `housekeeping rm` не инвалидирует размер зоны `projects` — она остаётся
  завышенной до истечения кеша. Завышение безопасно: порог автороста 85% может
  сработать чуть раньше, но не пропустит реальное переполнение.
  См. `pod/housekeeping.py::cmd_rm`.

## Разработка

```bash
python3 -m pytest -q                  # юнит-тесты, без Houdini и без сети
```

Живые проверки по отдельным нодам (тратят деньги, гасят поды за собой):

```bash
RPFARM_ROOT=$PWD <hython> scripts/smoke_scheduler_headless.py
RPFARM_ROOT=$PWD <hython> scripts/smoke_upload_headless.py
RPFARM_ROOT=$PWD <hython> scripts/smoke_download_headless.py
RPFARM_ROOT=$PWD <hython> scripts/smoke_stats_headless.py   # без сети и без подов
```

Общие части (сторож времени, отчёт по work item'ам, журнал, гашение подов)
живут в `rpfarm/smoke.py` — там же, где сам `rpfarm smoke`.

HDA лежат в репозитории в разобранном виде (`hda/*.hda/`, форма `hotl -t`).
Upload, Download и Stats пересобираются скриптами
`scripts/build_runpodfarm_*_hda.py`; у Scheduler'а сборщика нет — его
`PythonModule` правится прямо в `hda/runpodfarm_scheduler.hda/…/PythonModule`.
Что бы вы ни поменяли, `rpfarm setup` (или
`houdini_local.build_and_install_hdas`) схлопывает всё это `hotl -l` и кладёт
в `<prefs>/otls/`.

Сцена-фикстура для `rpfarm smoke` пересобирается так:

```bash
RPFARM_ROOT=$PWD <hython> scripts/build_smoke_fixture.py
```

Скрипт сам себя проверяет: перезагружает сохранённый файл и сверяет диапазоны
кадров и `roppath` (`verify: OK`). Диапазон, молча оставшийся сценным `1–240`,
стоил бы оплаченному поду 240 рендеров вместо трёх.

Секреты в репозиторий не попадают: значения живут только в
`~/.rpfarm/config.toml` (chmod 600) и в env подов, в репозитории — только имена.
